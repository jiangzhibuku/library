# 数据库索引与深分页 · 原理笔记

> 配套实验：D5（borrow 表 194,491 行，MySQL 8.0）
> 目的：把"为什么快"讲清楚，而不是背结论。

---

## 一、深分页为什么慢

### 1.1 `LIMIT offset, size` 到底做了什么

```sql
SELECT * FROM borrow ORDER BY id LIMIT 99990, 10;
```

数据库的执行顺序是：

1. 按 `ORDER BY id` 顺序扫描表（或用索引）
2. **读出前 `offset + size` 行**，也就是 100000 行
3. **丢弃前 99990 行**
4. 返回剩下的 10 行

**关键点：那 99990 行不是"跳过"，是"读出来再扔掉"。**

每一行都要做：读索引项 → 回表取整行数据 → 放进结果集 → 再丢弃。
行数越多，浪费的 IO 和 CPU 越多。

### 1.2 一个类比

想象一本没有页码的书，你要看第 10 万页：

- `LIMIT 99990, 10` = 从第 1 页开始，一页页翻到第 10 万页，才开始读
- `WHERE id > 99990` = 书有页码目录，直接翻到第 10 万页

**翻过的 99990 页，全是白费的力气。**

### 1.3 优化写法：游标分页（seek method）

```sql
SELECT * FROM borrow WHERE id > 99990 ORDER BY id LIMIT 10;
```

执行逻辑：

1. 在 B+树里**直接定位**到 `id > 99990` 的第一个位置（O(log n)）
2. 顺着叶子节点链表读 10 行（O(10)）
3. 结束

**前面那 99990 行，从来没有被读过。**

### 1.4 两种写法的执行计划对比（实测数据）

| 写法 | type | key | rows（EXPLAIN 估算） | 实测耗时 |
|---|---|---|---|---|
| `LIMIT 99990, 10` | `index` | PRIMARY | 100000 | 15.52 ms |
| `WHERE id > 99990 LIMIT 10` | `range` | PRIMARY | 97245 | 0.73 ms |

**注意一个容易误解的地方：**

`rows` 表示"**满足条件预计匹配的行数**"，不是"实际读取的行数"。
`WHERE id > 99990` 这个范围里确实有约 9.7 万行，所以 EXPLAIN 报 97245；
但因为有 `LIMIT 10`，**实际读到第 10 行就停止了**，EXPLAIN 并不体现这个提前停止。

**所以真正的差别在 `type`：**

| type | 执行方式 | 代价 |
|---|---|---|
| `index` | 全索引扫描：从第一行开始，顺序走过 10 万个索引项（每步还要回表取整行） | 贵 |
| `range` | 范围扫描：直接定位到 `id > 99990` 的起点，读 10 行就停 | 便宜 |

**一个是从头走，一个是直接跳。** 这是 15.52 ms 与 0.73 ms 的真实来源。

> 教训：读 EXPLAIN 不能只看 `rows`，`type` 往往更能说明执行方式。

### 1.5 这种优化的三个限制

1. **只能"下一页"，不能"跳到第 N 页"**
   用户点"第 500 页"时，你还是得知道第 500 页从哪个 id 开始。

2. **排序字段必须唯一且有序**
   一般用主键 `id`。如果用 `create_time` 排序，同一秒的数据可能重复，会漏行或重复。

3. **适合"滚动加载"，不适合"页码跳转"**
   所以：App 的无限滚动列表可以用，后台管理的页码表格不行。

### 1.6 另一种优化：延迟关联

如果不能改成分页游标，可以"先在索引里分页拿 id，再回表取数据"：

```sql
SELECT b.* FROM borrow b
JOIN (SELECT id FROM borrow ORDER BY id LIMIT 99990, 10) t
  ON b.id = t.id;
```

**原理**：子查询只取 `id` 这一列，可以走覆盖索引（不回表），扫描代价小得多；外层再按 10 个 id 回表。

## 二、索引是什么

### 2.1 一句话定义

**索引是一种额外的数据结构，保存"列值 → 数据行位置"的映射，让数据库不必逐行扫描就能找到目标行。**

MySQL 的 InnoDB 引擎用的是 **B+树**。

### 2.2 类比

一本书的**目录**：

- 没有目录：找"第 7 章"，只能从第一页开始翻
- 有目录：直接翻到"第 7 章 · 第 123 页"

索引就是数据库的目录。**它不改变数据本身，只是让你找得更快。**

### 2.3 为什么是 B+树

| 特性 | 好处 |
|---|---|
| **有序** | 支持范围查询（>、<、BETWEEN）和排序（ORDER BY） |
| **矮胖** | 3～4 层就能存千万级数据，每次查找只需几次磁盘 IO |
| **叶子节点用链表串起来** | 范围扫描时顺着链表读，不用回到根节点 |
| **非叶子节点只存键** | 一个 16KB 的页能放上千个键，树更矮 |

一次磁盘 IO 大约读 16KB（一页）。B+树的高度决定了 IO 次数：
**1000 万行数据，树高约 3 层 → 最多 3 次 IO 就能定位。**

### 2.4 索引的代价（很重要）

| 代价 | 说明 |
|---|---|
| **占空间** | 每个索引都是一份额外的数据 |
| **写入变慢** | INSERT / UPDATE / DELETE 都要同步维护索引 |
| **优化器可能选错** | 索引太多时，MySQL 可能选到不合适的那个 |

**结论：索引不是越多越好，只给"经常用来查的列"建索引。**

### 2.5 索引失效的五个常见场景

| 写法 | 为什么失效 |
|---|---|
| `WHERE YEAR(create_time) = 2024` | 对索引列做了函数运算，B+树无法定位 |
| `WHERE user_id = '500'`（列是数字，传字符串） | 隐式类型转换，等同于对列做函数 |
| `WHERE title LIKE '%Java'` | 前导模糊，无法从树的左边定位 |
| `WHERE status = 0`（联合索引是 `(user_id, status)`） | 不满足最左前缀 |
| `WHERE a = 1 OR b = 2`（b 无索引） | OR 会导致全表扫描 |

## 三、为什么要索引

### 3.1 两种查找方式的复杂度

| 方式 | 执行计划 type | 复杂度 | 194491 行的表现 |
|---|---|---|---|
| 全表扫描 | `ALL` | **O(n)**：逐行读、逐行判断 | 扫描 194491 行，25.96 ms |
| 索引查找 | `ref` | **O(log n) + 少量行** | 定位 81 行，0.40 ms |

**65 倍的差距，全部来自"要不要逐行扫描"。**

### 3.2 数据量越大，差距越大

| 数据量 | 全表扫描 | 索引查找 | 倍差 |
|---|---|---|---|
| 1 千行 | 几乎无感 | 几乎无感 | ≈1 |
| 10 万行 | 20–30 ms | <1 ms | ≈30 |
| 100 万行 | 200–300 ms | <1 ms | ≈300 |
| 1000 万行 | 秒级，可能超时 | <1 ms | **上千倍** |

**小数据量时索引"看不出效果"，这不是索引没用，是还没到那个量级。**

## 四、联合索引

### 4.1 是什么

把**多个列**放进同一棵 B+树，按 `(列1, 列2, 列3)` 的顺序排序。

```sql
ALTER TABLE borrow ADD INDEX idx_user_status (user_id, status);
```

它建立的排序规则是：**先按 user_id 排序，user_id 相同的再按 status 排序。**

### 4.2 最左前缀原则

索引 `(a, b, c)` 相当于建立了三棵"虚拟索引"：`(a)`、`(a,b)`、`(a,b,c)`。

| 查询条件 | 能否用上索引 |
|---|---|
| `WHERE a = ?` | ✅ 能用 |
| `WHERE a = ? AND b = ?` | ✅ 能用 |
| `WHERE a = ? AND b = ? AND c = ?` | ✅ 能用 |
| `WHERE a = ? AND c = ?` | ⚠️ 只能用 a，c 用不上 |
| `WHERE b = ?` | ❌ 用不上（跳过了 a） |
| `WHERE b = ? AND c = ?` | ❌ 用不上 |

**记忆口诀：从最左边开始，连续的才能用；中间断了，后面的全废。**

### 4.3 本例为什么用联合索引

查询是：

```sql
WHERE user_id = 500 AND status = 0
```

| 方案 | 执行过程 | 效果 |
|---|---|---|
| 只建 `(user_id)` | 定位到该用户的 ~194 行，再逐行判断 status | 读了 194 行，只要 81 行 |
| 建 `(user_id, status)` | 直接定位到"用户 500 且状态 0"的位置 | 精确读到 81 行 |

**联合索引把"两次过滤"合并成"一次定位"。**

### 4.4 顺序怎么定（三条规则）

1. **等值查询的列放前面**
   `user_id = ?` 和 `status = ?` 都是等值，都适合放前面。

2. **区分度高的列放左边**
   `user_id` 有 1000 个不同值，`status` 只有 2 个。
   `user_id` 先筛，能一步把范围缩到 1/1000。

3. **范围查询的列放最后**
   `WHERE a = ? AND b > ?` → 索引 `(a, b)`；
   因为 `b > ?` 之后的列无法再用于定位（B+树在范围之后是有序但不连续的）。

### 4.5 `key_len` 怎么读（判断用了几列）

实验数据：

```
key_len = 9
```

| 列 | 类型 | 字节 |
|---|---|---|
| `user_id` | BIGINT | 8 |
| `status` | TINYINT | 1 |
| 合计 | | **9** |

**`key_len = 9` → 两列全部命中。**

如果 `key_len = 8`，说明只用了 `user_id`，`status` 没进索引（比如查询里没写 status，或者顺序不对）。

**面试时说得出这一点，说明你真的看过执行计划，不是背的。**

## 五、本次实验的完整数据

### 5.1 实验条件

- 表：`borrow`
- 行数：**194,491**
- 查询：`SELECT ... WHERE user_id = 500 AND status = 0`
- 环境：MySQL 8.0 / InnoDB / 本地 SSD

### 5.2 优化前后对比

| 指标 | 优化前 | 优化后 | 变化 |
|---|---|---|---|
| `type` | `ALL`（全表扫描） | `ref`（索引查找） | — |
| `key` | `NULL` | `idx_user_status` | — |
| `key_len` | — | `9`（两列命中） | — |
| `rows` | **194,491** | **81** | **减少 2400 倍** |
| 耗时 | **25.96 ms** | **0.40 ms** | **快约 65 倍** |

### 5.3 深分页对比

| 写法 | type | rows（估算） | 耗时 |
|---|---|---|---|
| `ORDER BY id LIMIT 99990, 10` | `index` | 100000 | **15.52 ms** |
| `WHERE id > 99990 ORDER BY id LIMIT 10` | `range` | 97245 | **0.73 ms** |

差约 **21 倍**。注意 `rows` 一列看不出差距（97245 是范围估算，LIMIT 会提前停止），真正的差别在 `type`：`index` 是顺序扫描，`range` 是定位后读取。

## 六、面试时怎么说（三句话版本）

> **第一句（做了什么）**：borrow 表有 19 万行数据，`WHERE user_id AND status` 的查询走全表扫描要 26 毫秒。
>
> **第二句（怎么做的）**：加了 `(user_id, status)` 联合索引，执行计划从 `type=ALL` 变成 `type=ref`，扫描行数从 19 万降到 81，耗时降到 0.4 毫秒。
>
> **第三句（为什么有效）**：`key_len=9` 说明两列都命中了索引；联合索引把"先按 user_id 筛、再逐行判断 status"合并成一次定位。

**再加一句深分页的，就够了：**

> 另外做过深分页对比：`LIMIT 99990,10` 要扫描 10 万行，改成 `WHERE id > 99990` 后只读 10 行——因为前者是"读出来再丢弃"，后者是"直接定位"。

## 七、一分钟自测

1. 为什么 `LIMIT 99990, 10` 慢？—— 因为它要真的读出 10 万行再丢弃前 99990 行。
2. 索引的本质是什么？—— "列值 → 行位置"的映射，InnoDB 用 B+树实现。
3. 索引有什么代价？—— 占空间、拖慢写入、可能选错。
4. 联合索引 `(a,b,c)` 能用于 `WHERE b = ?` 吗？—— 不能，违反最左前缀。
5. `key_len` 能说明什么？—— 索引实际用上了哪几列。
6. 深分页优化的限制是什么？—— 只能"下一页"，不能"跳到第 N 页"。
